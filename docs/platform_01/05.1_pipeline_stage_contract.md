# Research Knowledge Graph Builder (RKGB)

# Processing Engine Specification

## Document 05.1 — Pipeline Stage Contract

**Version:** 1.0

---

# 1. Purpose

The Pipeline Stage Contract defines the standard lifecycle, interface, and behavioral rules that every processing stage within the RKGB platform must implement.

It ensures that all stages:

* Behave consistently
* Are independently testable
* Support retries
* Support checkpointing
* Can be reordered
* Can execute in parallel where appropriate
* Can be orchestrated by different workflow engines

Every processing stage—current or future—must conform to this contract.

---

# 2. Position in the Architecture

```text
Workflow
      │
      ▼
Pipeline Manager
      │
      ▼
Pipeline Stage
      │
      ▼
Pipeline Context
```

The Pipeline Manager interacts only with the stage contract.

It never depends on implementation details.

---

# 3. Design Philosophy

Each stage should represent **one business capability**.

Examples

✓ Validate Document

✓ Extract Metadata

✓ Detect Sections

✓ Extract Authors

✓ Resolve Citations

✓ Build Knowledge Graph

✗ "Process Document"

A stage should perform exactly one responsibility.

---

# 4. Stage Lifecycle

Every stage follows the same execution lifecycle.

```text
Initialize

↓

Pre-Validation

↓

Execute

↓

Post-Processing

↓

Checkpoint

↓

Complete

↓

Cleanup
```

If execution fails:

```text
Execute

↓

Exception

↓

Rollback

↓

Cleanup

↓

Failed
```

---

# 5. Standard Interface

Every stage must expose the following lifecycle methods.

```text
initialize(context)

↓

validate(context)

↓

execute(context)

↓

post_process(context)

↓

rollback(context)

↓

cleanup(context)
```

Each method has a clearly defined responsibility.

---

# 6. initialize()

Purpose

Prepare the stage for execution.

Typical activities

* Load configuration
* Acquire lightweight resources
* Verify prerequisites
* Initialize metrics
* Register execution metadata

The Pipeline Context must not be modified beyond initialization metadata.

---

# 7. validate()

Purpose

Ensure that required inputs exist before execution.

Examples

Metadata Extraction Stage

Requires

* Valid document
* Existing file

NER Stage

Requires

* Parsed text
* Detected language

Validation failures should produce descriptive business errors rather than runtime exceptions.

---

# 8. execute()

Purpose

Perform the core business operation.

Examples

Document Validation

↓

Verify PDF

Metadata Extraction

↓

Extract metadata

NER

↓

Identify entities

Graph Construction

↓

Create nodes and relationships

Only this method should perform the primary business work.

---

# 9. post_process()

Purpose

Finalize outputs.

Examples

* Normalize values
* Remove duplicates
* Update statistics
* Append domain events
* Produce execution summary

Post-processing should not repeat the primary work of the stage.

---

# 10. rollback()

Purpose

Undo changes made by the stage where feasible.

Examples

* Delete temporary files
* Remove incomplete graph objects
* Release locks
* Reverse partial persistence

Not every stage requires a rollback implementation, but every stage must define its rollback behavior.

---

# 11. cleanup()

Purpose

Release resources regardless of success or failure.

Examples

* Close file handles
* Dispose parser instances
* Clear temporary caches
* Flush metrics

Cleanup is always executed.

---

# 12. Stage States

Every stage progresses through defined states.

```text
Pending

↓

Initializing

↓

Validating

↓

Running

↓

Post Processing

↓

Completed
```

Failure path

```text
Running

↓

Failed

↓

Rolling Back

↓

Cleaned Up
```

These states are recorded in the Pipeline Context.

---

# 13. Stage Input

Every stage receives a single object.

```text
PipelineContext
```

Stages must never accept arbitrary parameter lists.

All required data must be obtained from the context.

---

# 14. Stage Output

Every stage returns the same Pipeline Context instance after enriching it.

```text
PipelineContext

↓

Stage

↓

PipelineContext
```

The context evolves as it moves through the pipeline.

---

# 15. Stage Ownership

Each stage owns a specific section of the Pipeline Context.

| Stage                | Primary Context Section |
| -------------------- | ----------------------- |
| Validation           | Document State          |
| Metadata Extraction  | Document Metadata       |
| Parsing              | NLP Artifacts           |
| NER                  | Entities                |
| Relation Extraction  | Relations               |
| Graph Builder        | Graph Artifacts         |
| Embedding Generation | Embeddings              |

Stages should not modify sections owned by unrelated stages except through well-defined extension points.

---

# 16. Stage Dependencies

Stages declare explicit dependencies.

Examples

NER depends on:

* Parsed text

Graph Builder depends on:

* Entities
* Relations
* Ontology mappings

The Pipeline Manager uses dependency information to determine execution order and identify opportunities for parallel execution.

---

# 17. Idempotency

Stages should be idempotent whenever possible.

Running a stage multiple times with the same input should produce the same result without unintended side effects.

This simplifies retries and recovery.

---

# 18. Checkpoint Integration

Stages define whether a checkpoint should be created after successful execution.

Example

```text
Validation

↓

Checkpoint

Metadata

↓

Checkpoint

NER

↓

No Checkpoint

Graph Builder

↓

Checkpoint
```

Checkpoint policy may be configured by the workflow.

---

# 19. Event Integration

Stages do not publish events directly.

Instead, they append domain events to the Pipeline Context.

Examples

* MetadataExtracted
* AuthorsResolved
* KnowledgeGraphBuilt

The workflow or event dispatcher is responsible for publishing them.

---

# 20. Logging and Metrics

Every stage records:

* Start time
* End time
* Duration
* Status
* Warning count
* Error count
* Items processed

Metrics are stored in the Pipeline Context and forwarded to the observability infrastructure.

---

# 21. Error Classification

Errors fall into three categories.

Business Errors

* Invalid PDF
* Missing DOI
* Unknown citation format

Recoverable Errors

* Temporary parser failure
* Network timeout
* Missing optional metadata

Fatal Errors

* Corrupted document
* Invalid pipeline configuration
* Persistence failure

The stage should classify errors to support retry policies.

---

# 22. Parallel Execution

Stages may declare themselves as:

* Sequential
* Parallel-safe
* Mutually exclusive

Example

```text
Parsed Text

├── Keyword Extraction

├── NER

├── Section Detection

└── Citation Detection
```

The Pipeline Manager schedules compatible stages concurrently.

---

# 23. Configuration

Stages should receive configuration through dependency injection or the Pipeline Context.

Configuration should not be hard-coded.

Examples

* Confidence thresholds
* Parser selection
* Maximum retries
* Language models

---

# 24. Testing Strategy

Each stage is tested independently.

Unit tests verify:

* Validation behavior
* Business logic
* Context enrichment
* Error handling
* Rollback
* Cleanup

Integration tests verify interoperability with adjacent stages.

---

# 25. Extensibility

New stages can be added without modifying the Pipeline Manager.

Examples

Phase 2

* EmbeddingGenerationStage
* SemanticChunkingStage

Phase 3

* AgentPlanningStage
* ToolExecutionStage

Phase 4

* LinkPredictionStage
* GraphEmbeddingStage

Phase 5

* KafkaPublishingStage
* SparkExecutionStage
* FeatureStoreStage

The manager discovers and executes stages through the common contract.

---

# 26. Relationship with Workflows

A workflow selects, configures, and orders stages.

The stage contract defines how each stage behaves.

The workflow defines why and when the stage executes.

This separation keeps orchestration independent from implementation.

---

# 27. Guiding Principle

A Pipeline Stage is a self-contained processing component that performs one business capability, enriches the Pipeline Context, and obeys a standardized execution lifecycle.

By enforcing a common contract, the RKGB processing engine gains consistency, composability, fault tolerance, observability, and the flexibility to evolve from a single-process application into a distributed AI platform powered by workflows, event buses, Kafka, GraphRAG, autonomous agents, and large-scale data processing.
