# Research Knowledge Graph Builder (RKGB)

# Implementation Specification

## Document 03.6 — Application DTOs & Mapping Layer

**Version:** 1.0

---

# 1. Purpose

This document defines the Data Transfer Object (DTO) layer used to exchange data between external interfaces and the application.

DTOs provide a stable contract between clients and the RKGB platform while isolating the domain model from transport concerns.

The DTO layer enables:

* API stability
* Versioned contracts
* Validation at system boundaries
* Separation of concerns
* Independent evolution of the domain model
* Reusable contracts for REST, GraphQL, CLI, Kafka, and future AI agents

---

# 2. Position in the Architecture

```text
External Client
      │
      ▼
REST API
      │
      ▼
Request DTO
      │
      ▼
Command / Query
      │
      ▼
Handler
      │
      ▼
Application Service
      │
      ▼
Domain Model
      │
      ▼
Repository
```

Response flow:

```text
Repository
      │
      ▼
Domain Model
      │
      ▼
Response DTO
      │
      ▼
REST API
      │
      ▼
Client
```

The API never exposes domain entities directly.

---

# 3. DTO Categories

The platform defines five DTO categories.

```text
Request DTOs

↓

Command DTOs

↓

Query DTOs

↓

Response DTOs

↓

Event DTOs
```

Each category has a distinct responsibility.

---

# 4. Request DTOs

Request DTOs represent data received from external clients.

Examples

```text
UploadDocumentRequest

BuildGraphRequest

SearchRequest

CreatePaperRequest
```

Responsibilities

* Input validation
* Type coercion
* Default values
* API documentation

Request DTOs contain no business logic.

---

# 5. Command DTOs

Command DTOs encapsulate data required to execute a business operation.

Examples

```text
UploadDocumentCommand

ArchiveDocumentCommand

ExtractMetadataCommand

BuildKnowledgeGraphCommand
```

Command DTOs are immutable after creation.

---

# 6. Query DTOs

Query DTOs represent read operations.

Examples

```text
GetPaperQuery

SearchKnowledgeGraphQuery

SemanticSearchQuery

ListDatasetsQuery
```

Queries define filtering, sorting, pagination, and retrieval criteria.

---

# 7. Response DTOs

Response DTOs shape the data returned to clients.

Examples

```text
DocumentResponse

PaperSummaryResponse

AuthorResponse

GraphResponse

SearchResponse
```

They expose only the information required by the client.

Internal identifiers or implementation details should not leak through these objects.

---

# 8. Read Models

Complex queries often require specialized read models.

Examples

```text
PaperSearchResult

AuthorProfile

KnowledgeGraphSummary

CitationNetwork

DocumentOverview
```

Read models may aggregate information from multiple domain entities.

They are optimized for consumption, not persistence.

---

# 9. Event DTOs

Event DTOs define payloads published on the Event Bus.

Examples

```text
DocumentUploadedEvent

PaperExtractedEvent

KnowledgeGraphBuiltEvent

OntologyValidatedEvent
```

These DTOs should contain sufficient information for subscribers while remaining independent of transport technology.

---

# 10. Mapping Layer

DTOs are converted to and from domain models through dedicated mappers.

```text
Request DTO
      │
      ▼
Mapper
      │
      ▼
Domain Model
```

Response:

```text
Domain Model
      │
      ▼
Mapper
      │
      ▼
Response DTO
```

Mapping logic must not reside in controllers or repositories.

---

# 11. Mapper Responsibilities

A mapper is responsible for:

* Translating DTOs into domain entities
* Translating domain entities into response models
* Normalizing values where appropriate
* Handling optional fields
* Preserving domain invariants

Mappers do not perform business validation.

---

# 12. Mapper Catalogue

Examples include:

```text
DocumentMapper

PaperMapper

AuthorMapper

DatasetMapper

AlgorithmMapper

KnowledgeGraphMapper

OntologyMapper
```

Each mapper is responsible for one aggregate or bounded context.

---

# 13. Validation Strategy

Validation occurs at multiple layers.

| Layer           | Responsibility                      |
| --------------- | ----------------------------------- |
| Request DTO     | Syntax, required fields, data types |
| Command Handler | Business preconditions              |
| Domain Model    | Business invariants                 |
| Repository      | Persistence constraints             |

This layered validation prevents invalid data from propagating through the system.

---

# 14. API Versioning

DTOs are versioned independently of the domain model.

Example

```text
api/
└── v1/
    ├── requests/
    ├── responses/
└── v2/
    ├── requests/
    ├── responses/
```

Versioning allows the API to evolve without breaking existing clients.

# 16. Future Integrations

The DTO layer supports additional interfaces without changing the domain model.

Examples

* GraphQL
* gRPC
* Kafka message payloads
* MCP tool interfaces
* AI agent communication
* Batch processing jobs

Each integration defines its own DTOs while sharing the same application services.

---

# 18. Guiding Principle

DTOs define the contracts between RKGB and the outside world.

The domain model defines the business.

Repositories define persistence.

Keeping these concerns separate ensures that changes to APIs, storage technologies, or communication protocols do not require changes to the core business model.

This separation is essential for a long-lived platform expected to support REST APIs, semantic search, GraphRAG, Agentic AI, Kafka-based messaging, and future distributed AI services.
