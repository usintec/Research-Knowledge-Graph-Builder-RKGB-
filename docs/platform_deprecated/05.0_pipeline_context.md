# Research Knowledge Graph Builder (RKGB)

# Processing Engine Specification

## Document 05.0 — Pipeline Context

**Version:** 1.0

---

# 1. Purpose

The Pipeline Context is the canonical execution object passed between every stage of the RKGB processing pipeline.

Rather than passing multiple objects, dictionaries, or temporary variables between stages, the pipeline exchanges a single context object that accumulates knowledge as processing progresses.

The Pipeline Context provides:

* Shared execution state
* Aggregate transport
* Intermediate AI artifacts
* Stage coordination
* Error propagation
* Execution metadata
* Checkpoint support

It is the execution backbone of the processing engine.

---

# 2. Position in the Architecture

```text

Pipeline Context

↓

Stage 1

↓

Pipeline Context

↓

Stage 2

↓

Pipeline Context

↓

Stage N
```

Every stage receives and returns the same context object.

---

# 3. Design Philosophy

The Pipeline Context follows three principles:

### Single Execution Object

A workflow owns exactly one Pipeline Context instance for each execution.

---

### Progressive Enrichment

Each stage enriches the context.

No stage should remove information produced by earlier stages unless explicitly invalidated.

---

### Immutable Business Identity

The business identity (document, correlation ID, workflow ID) remains constant throughout execution.

# 5. High-Level Structure

The Pipeline Context is composed of several logical sections.

```text
PipelineContext

├── Execution Information

├── Document State

├── Domain Aggregates

├── NLP Artifacts

├── Graph Artifacts

├── Embeddings

├── Processing Results

├── Events

├── Diagnostics

└── Extension Storage
```

Each section has a defined responsibility.

---

# 6. Execution Information

Tracks workflow execution.

Attributes include:

* pipeline_id
* workflow_id
* correlation_id
* execution_id
* current_stage
* previous_stage
* next_stage
* status
* started_at
* completed_at
* elapsed_time

Purpose

Supports tracing, monitoring, retries, and distributed execution.

---

# 7. Document State

Contains information related to the uploaded document.

Objects

* ManagedDocument
* DocumentMetadata
* DocumentVersion
* StorageLocation

These objects originate in Stage 1 and remain available throughout the pipeline.

---

# 8. Domain Aggregates

Stores reconstructed business objects.

Examples

* Paper
* Author
* Institution
* Dataset
* Algorithm
* Method
* Task
* Metric
* ResearchArea
* Citation
* KnowledgeGraph

Each aggregate is progressively enriched by later stages.

---

# 9. NLP Artifacts

Intermediate outputs produced by language processing.

Examples

* Raw text
* Clean text
* Sections
* Paragraphs
* Sentences
* Tokens
* Lemmas
* Named entities
* Entity spans
* Part-of-speech tags
* Dependency trees
* Relations
* Keywords
* Topics
* Summaries

These artifacts support downstream extraction and reasoning.

---

# 10. Graph Artifacts

Stores graph-related intermediate results.

Examples

* Graph nodes
* Graph relationships
* Ontology mappings
* Cypher fragments
* RDF triples (future)
* OWL classes (future)
* Validation reports

The finalized KnowledgeGraph aggregate is produced from these artifacts.

---

# 11. Embedding Artifacts

Reserved for semantic search.

Examples

* Document embedding
* Section embeddings
* Entity embeddings
* Citation embeddings
* Graph embeddings (future)

Initially empty in Phase 1.

---

# 12. Processing Results

Each stage records its outcome.

Examples

```text

SUCCESS

Metadata Extraction

SUCCESS

NER

SUCCESS

```

Each result includes:

* status
* execution time
* warnings
* errors
* output summary

---

# 13. Event Collection

Stages do not publish events directly.

Instead, they append domain events to the context.

Examples

* DocumentValidated
* MetadataExtracted
* PaperCreated
* GraphBuilt
* GraphValidated

The workflow publishes events after successful completion or at configured checkpoints.

---

# 14. Diagnostics

Collects operational information.

Examples

* Warning messages
* Recoverable errors
* Performance metrics
* Stage durations
* Retry counts
* Memory usage
* CPU usage (future)

Useful for debugging and observability.

---

# 15. Extension Storage

Provides a flexible area for future capabilities.

Examples

* Agent memory
* User annotations
* Experimental features
* Plugin outputs
* Temporary caches

Extensions should be namespaced to avoid collisions.

---

# 16. Stage Interaction

Every stage follows the same contract.

```text
Pipeline Context

↓

Read Required Data

↓

Perform Work

↓

Update Context

↓

Return Context
```

Stages communicate only through the context.

---

# 17. Data Ownership

Each section has a primary owner.

| Section           | Primary Producer    |
| ----------------- | ------------------- |
| Document State    | Document Management |
| NLP Artifacts     | NLP Pipeline        |
| Domain Aggregates | Domain Services     |
| Graph Artifacts   | Graph Builder       |
| Embeddings        | Embedding Service   |
| Diagnostics       | All Stages          |
| Events            | All Stages          |

Consumers may read from any completed section but should modify only the sections they own.

---

# 18. Checkpointing

The context supports checkpoint persistence.

Example

```text
Validation

↓

Checkpoint

↓

Metadata

↓

Checkpoint

↓

NER

↓

Checkpoint

↓

Graph

↓

Completed
```

If execution fails, processing can resume from the latest checkpoint rather than restarting from the beginning.

---

# 19. Parallel Execution

Independent stages may execute concurrently.

Example

```text
Parsed Text

├── Keyword Extraction
├── NER
├── Section Detection
└── Citation Detection
```

Each stage updates different areas of the context, after which the workflow synchronizes the results.

This enables efficient multicore execution and future distributed processing.

---

# 20. Distributed Processing

Future Kafka integration serializes the Pipeline Context (or selected sections) into messages.

Workers consume the context, execute a stage, enrich it, and republish it.

The business contract remains unchanged whether execution is local or distributed.

---

# 21. Serialization

The context should support multiple serialization formats.

Examples

* JSON
* MessagePack
* Protocol Buffers (future)

Only portable data should be serialized; infrastructure resources such as database connections must never be embedded.

---

# 22. Error Recovery

Recoverable failures are recorded within the context.

Examples

* Missing DOI
* Unknown institution
* Low-confidence entity

Fatal failures terminate the workflow, preserving the context for inspection and possible retry.

---

# 23. Testing Strategy

Pipeline stages are tested using synthetic Pipeline Context instances.

This allows each stage to be exercised independently without requiring the full pipeline.

Integration tests verify that context enrichment remains consistent across multiple stages.

---

# 24. Future Evolution

The Pipeline Context is designed to grow with the platform.

Phase 2

* Embedding artifacts
* Semantic retrieval metadata

Phase 3

* Agent memory
* Planning state
* Tool execution history

Phase 4

* Graph embeddings
* Link prediction artifacts

Phase 5

* Kafka offsets
* Airflow run metadata
* Feature store references

New sections should be additive to preserve backward compatibility.

---

# 25. Guiding Principle

The Pipeline Context is the single source of truth for an in-flight processing execution.

Every workflow, processing stage, AI component, and future distributed worker communicates through this object rather than exchanging ad hoc data structures.

By centralizing execution state, the RKGB platform gains consistency, observability, extensibility, and resilience while providing a stable foundation for semantic knowledge graph construction, GraphRAG, autonomous research agents, graph machine learning, and large-scale distributed AI processing.
