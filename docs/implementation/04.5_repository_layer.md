# Research Knowledge Graph Builder (RKGB)

# Implementation Specification

## Document 04.5 — Persistence Mapping Layer

**Version:** 1.0

---

# 1. Purpose

The Persistence Mapping Layer is responsible for translating between the RKGB domain model and the underlying persistence technologies.

It isolates storage-specific schemas from business objects and ensures that repositories remain focused on aggregate persistence rather than object transformation.

The mapping layer enables:

* Storage independence
* Rich domain models
* Multiple persistence technologies
* Schema evolution
* Easier testing
* Migration support

---

# 2. Position in the Architecture

```text
Application Service
        │
        ▼
Repository Interface
        │
        ▼
Infrastructure Repository
        │
        ▼
Persistence Mapper
        │
        ▼
Storage Backend
```

Repositories coordinate persistence.

Mappers perform transformations.

---

# 3. Why a Mapping Layer?

Without a mapper:

```text
Repository

├── Cypher

├── SQL

├── Object Construction

├── Relationship Mapping

├── Property Conversion

└── Validation
```

The repository quickly becomes large, difficult to test, and tightly coupled to storage schemas.

With a mapper:

```text
Repository

↓

Persistence Mapper

↓

Neo4j / PostgreSQL / Files
```

Responsibilities are clearly separated.

---

# 4. Mapping Philosophy

The mapping layer translates between four representations of the same business concept.

```text
DTO

↓

Domain Aggregate

↓

Persistence Model

↓

Storage Representation
```

Example:

```
UploadDocumentRequest

↓

ManagedDocument

↓

DocumentRecord

↓

SQL Row
```

---

# 5. Mapping Categories

The platform defines five mapper categories.

```text
Aggregate Mappers

↓

Graph Mappers

↓

Relational Mappers

↓

File Mappers

↓

Future Vector Mappers
```

Each category targets one storage model.

---

# 6. Aggregate Mappers

Aggregate mappers reconstruct complete aggregates.

Examples

```text
ManagedDocumentMapper

PaperMapper

AuthorMapper

KnowledgeGraphMapper
```

Responsibilities

* Build aggregates
* Restore invariants
* Populate child entities
* Preserve identity

---

# 7. Neo4j Mappers

Neo4j mappers convert aggregates into graph structures.

Examples

```text
PaperNeo4jMapper

AuthorNeo4jMapper

InstitutionNeo4jMapper

DatasetNeo4jMapper

KnowledgeGraphNeo4jMapper
```

Responsibilities

* Create node properties
* Create relationship properties
* Generate Cypher parameters
* Reconstruct aggregates from graph traversals

---

# 8. Relational Mappers

Relational mappers convert aggregates into relational records.

Examples

```text
ManagedDocumentSqlMapper

ProcessingHistorySqlMapper

WorkflowExecutionSqlMapper
```

Responsibilities

* Table mapping
* Foreign key mapping
* Type conversion
* Timestamp conversion

---

# 9. File Mappers

File mappers describe how binary assets relate to domain objects.

Examples

```text
PdfStorageMapper

ExportMapper

ArtifactMapper
```

Responsibilities

* Storage paths
* Version identifiers
* File metadata
* Integrity checks

---

# 10. Future Vector Mappers

Future embedding storage requires specialized mapping.

Examples

```text
EmbeddingVectorMapper

SemanticChunkMapper

SearchIndexMapper
```

Responsibilities

* Embedding serialization
* Metadata attachment
* Chunk identifiers
* Vector payload construction

---

# 11. Mapper Responsibilities

A persistence mapper may:

* Convert domain objects to storage models
* Convert storage models to domain objects
* Normalize data types
* Populate child entities
* Resolve nested structures

A mapper must not:

* Execute queries
* Open transactions
* Publish events
* Apply business rules
* Invoke external services

---

# 12. Mapping Flow

Saving an aggregate:

```text
Paper

↓

PaperNeo4jMapper

↓

Cypher Parameters

↓

Neo4j Repository

↓

Database
```

Loading an aggregate:

```text
Neo4j

↓

Cypher Result

↓

PaperNeo4jMapper

↓

Paper Aggregate
```

---

# 13. Aggregate Reconstruction

Many aggregates span multiple records or graph nodes.

Example

```
Paper

├── Authors

├── Datasets

├── Algorithms

├── Citations

└── Metrics
```

The mapper is responsible for reconstructing the aggregate from distributed persistence data.

---

# 14. Relationship Mapping

Graph relationships are mapped independently.

Example

```
Paper

WRITTEN_BY

Author
```

Maps to

```text
(:Paper)-[:WRITTEN_BY]->(:Author)
```

Relationship properties are preserved during conversion.

---

# 15. Type Conversion

The mapper performs storage-specific type conversion.

Examples

| Domain   | Storage            |
| -------- | ------------------ |
| UUID     | String             |
| datetime | ISO-8601 Timestamp |
| Enum     | String             |
| FileSize | Integer            |
| DOI      | String             |
| ORCID    | String             |

Conversion rules are centralized within the mapper.

---

# 16. Schema Evolution

The mapping layer isolates domain models from schema changes.

Example

Neo4j Schema v1

```
publicationYear
```

Neo4j Schema v2

```
year
```

Only the mapper changes.

The domain model remains unchanged.

---

# 17. Multiple Storage Targets

The same aggregate may be stored in multiple technologies.

Example

Paper

↓

Neo4j Mapper

↓

Graph Database

and

Paper

↓

Search Mapper

↓

Search Index

The application still interacts with a single `Paper` aggregate.

---

# 18. Mapper Registry

The platform maintains a registry of mappers.

Example

```text
MapperRegistry

├── PaperNeo4jMapper

├── AuthorNeo4jMapper

├── ManagedDocumentSqlMapper

└── PdfStorageMapper
```

Repositories request mappers through the registry or dependency injection container.

---

# 19. Testing Strategy

Mappers are tested independently.

Unit tests verify:

* Correct property mapping
* Relationship mapping
* Aggregate reconstruction
* Type conversion
* Schema compatibility

Repository tests should assume mappers are already validated.

---

# 20. Error Handling

Mapping failures raise mapping-specific exceptions.

Examples

* MappingException
* MissingPropertyException
* InvalidNodeException
* UnsupportedSchemaVersionException

Repositories translate these into persistence errors when appropriate.

---

# 21. Future Evolution

The mapping layer is designed to support future capabilities.

Phase 2

* Embedding serialization
* Semantic chunk mapping

Phase 3

* Agent memory mapping
* Tool execution state mapping

Phase 4

* Graph embedding mapping
* Recommendation graph mapping

Phase 5

* Event projection mapping
* Data lake mapping
* Feature store mapping

New storage technologies should require only new mapper implementations, not changes to repositories or domain models.

---

# 22. Guiding Principle

The Persistence Mapping Layer is the translation boundary between business concepts and storage representations.

Repositories manage persistence.

Mappers manage transformation.

By separating these concerns, the RKGB platform remains resilient to schema evolution, storage migration, and future expansion into RDF, OWL, GraphRAG, vector databases, and distributed AI infrastructure while preserving a clean and expressive domain model.
