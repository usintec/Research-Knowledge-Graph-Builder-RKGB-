# Research Knowledge Graph Builder (RKGB)

# Processing Engine Specification

## Document 05.2 — Pipeline Manager (Execution Engine)

**Version:** 1.0

---

# 1. Purpose

The Pipeline Manager is the execution engine of the RKGB processing framework.

It coordinates the execution of processing stages, manages execution state, enforces stage ordering, handles failures, records metrics, and returns a fully enriched Pipeline Context.

The Pipeline Manager does not perform business logic itself. Instead, it orchestrates the execution of specialized processing stages according to a workflow-defined execution plan.

---

# 2. Position in the Architecture

```text
Workflow
      │
      ▼
Pipeline Manager
      │
      ├──────────────┐
      ▼              ▼
Execution Planner  Execution Runtime
      │              │
      └──────┬───────┘
             ▼
      Pipeline Context
             │
             ▼
      Pipeline Stages
```

The manager coordinates planning and execution while remaining independent of stage implementations.

---

# 3. Responsibilities

The Pipeline Manager is responsible for:

* Building execution plans
* Resolving stage dependencies
* Initializing the Pipeline Context
* Invoking the Execution Runtime
* Coordinating checkpointing
* Managing retries
* Collecting execution metrics
* Returning the completed Pipeline Context

The Pipeline Manager must not implement business logic or manipulate domain aggregates directly.

---

# 4. Internal Components

The execution engine consists of three collaborating components:

| Component         | Responsibility         |
| ----------------- | ---------------------- |
| Pipeline Manager  | Coordinates execution  |
| Execution Planner | Builds execution plans |
| Execution Runtime | Executes stages        |

This separation improves maintainability and extensibility.

---

# 5. Execution Planner

The Execution Planner transforms a workflow definition into an executable plan.

Responsibilities include:

* Discovering stages
* Resolving dependencies
* Detecting circular dependencies
* Determining execution order
* Identifying parallel-safe stages
* Applying conditional execution rules
* Generating retry policies

The output is an immutable Execution Plan.

---

# 6. Execution Plan

An Execution Plan is an ordered representation of stage execution.

It contains:

* Stage sequence
* Dependencies
* Parallel execution groups
* Conditional branches
* Checkpoint locations
* Retry configuration

The plan is generated once and executed without modification.

---

# 7. Execution Runtime

The Execution Runtime executes the Execution Plan.

Responsibilities include:

* Initializing stages
* Invoking lifecycle methods
* Updating the Pipeline Context
* Recording execution metrics
* Handling exceptions
* Managing rollback
* Performing cleanup

The runtime is the only component that directly invokes stage methods.

---

# 8. Execution Lifecycle

```text
Workflow

↓

Execution Planner

↓

Execution Plan

↓

Execution Runtime

↓

Pipeline Context

↓

Completed
```

Planning and execution remain distinct phases.

---

# 9. Stage Scheduling

The runtime schedules stages according to the Execution Plan.

Scheduling modes include:

* Sequential
* Parallel
* Conditional
* Optional
* Retryable

Future schedulers may support distributed execution.

---

# 10. Dependency Resolution

The planner constructs a directed acyclic graph (DAG) of stage dependencies.

Example

```text
Validate
      │
      ▼
Parse
      │
      ├──────────────┐
      ▼              ▼
NER          Section Detection
      │              │
      └──────┬───────┘
             ▼
     Graph Builder
```

The planner validates the graph before execution.

---

# 11. Parallel Execution

Independent stages may execute concurrently.

The runtime synchronizes updates to the Pipeline Context before downstream stages begin.

Parallel execution policies are defined by the Execution Plan.

---

# 12. Checkpoint Management

The runtime creates checkpoints at configured boundaries.

Responsibilities include:

* Persisting Pipeline Context state
* Recording completed stages
* Supporting restart after failure

Checkpoint creation is transparent to individual stages.

---

# 13. Retry Management

Retry policies are applied by the runtime.

Policy parameters include:

* Maximum attempts
* Retry interval
* Exponential backoff
* Retryable exception types

Stages remain unaware of retry logic.

---

# 14. Rollback Coordination

When a stage fails irrecoverably, the runtime coordinates rollback according to the Execution Plan.

Rollback strategies may include:

* Stage rollback
* Workflow compensation
* Partial cleanup
* Manual intervention

---

# 15. Event Coordination

Stages append domain events to the Pipeline Context.

The runtime collects these events and passes them to the Event Dispatcher at configured synchronization points.

---

# 16. Metrics Collection

The runtime records:

* Stage duration
* Workflow duration
* Success rate
* Failure rate
* Retry count
* Queue time
* Resource usage (future)

Metrics support monitoring and optimization.

---

# 17. Observability

The Pipeline Manager integrates with the logging and tracing infrastructure.

Each execution is identified by:

* Pipeline ID
* Workflow ID
* Correlation ID
* Execution ID

This enables end-to-end traceability across distributed systems.

---

# 18. Failure Handling

Failures are categorized as:

* Validation failures
* Recoverable execution failures
* Fatal execution failures
* Infrastructure failures

The runtime applies the appropriate retry or rollback strategy based on classification.

---

---

# 20. Testing Strategy

The Pipeline Manager is tested independently from individual stages.

Tests verify:

* Plan generation
* Dependency resolution
* Scheduling
* Parallel execution
* Retry behavior
* Rollback coordination
* Checkpoint creation
* Metrics collection

Execution stages are replaced with mock implementations during manager testing.

---

# 21. Guiding Principle

The Pipeline Manager is the execution kernel of the RKGB processing engine.

It transforms workflow definitions into executable plans, coordinates stage execution through a standardized runtime, and ensures that every processing pipeline executes consistently, reliably, and observably.

By separating planning, execution, and business logic, the RKGB platform gains a scalable foundation capable of supporting semantic knowledge graph construction, GraphRAG, autonomous research agents, graph machine learning, and future distributed AI processing without architectural redesign.
