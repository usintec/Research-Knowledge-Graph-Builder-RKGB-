# Research Knowledge Graph Builder (RKGB)

# Implementation Specification

## Document 06.1 — Document Management Pipeline Class Design (CQRS Edition)

**Version:** 2.0

---

# 1. Purpose

This document defines the implementation blueprint for the Document Management Pipeline using the RKGB CQRS-lite Application Layer.

The Document Management Pipeline is responsible for orchestrating the ingestion workflow of research documents. It coordinates execution through the Pipeline Manager and delegates all business operations to the Application Layer via Commands and Queries.

The pipeline itself contains **no business logic**.

---

# 3. Responsibilities

The Document Management Pipeline is responsible for:

* Executing pipeline stages in order
* Passing the Pipeline Context between stages
* Delegating business operations through Commands and Queries
* Collecting execution metrics
* Recording checkpoints
* Publishing pipeline-level events
* Returning the completed Pipeline Context

The pipeline does **not**:

* Validate business rules
* Access repositories directly
* Call infrastructure services
* Persist data
* Contain domain logic

# 5. Relationship with the Application Layer

Each pipeline stage communicates exclusively with the Application Layer.

```text

↓

↓

↓

↓

↓

```

Pipeline stages never call repositories or domain services directly.

---

# 6. DocumentManagementPipeline

## Responsibility

The pipeline is the public entry point for document ingestion.

Responsibilities include:

* Creating the Pipeline Context
* Loading the Pipeline Definition
* Invoking the Pipeline Manager
* Returning the completed context

The pipeline is intentionally lightweight.

---

# 7. PipelineBuilder

The PipelineBuilder constructs the executable pipeline.

Responsibilities include:

* Selecting enabled stages
* Applying execution profiles
* Resolving feature flags
* Producing the Pipeline Definition

No stage implementations are hard-coded into the pipeline.

---

# 8. Pipeline Stages

Every stage implements the common Pipeline Stage Contract.

Responsibilities:

* Read required data from the Pipeline Context
* Construct Commands or Queries
* Dispatch messages through the appropriate Bus
* Store returned results in the Pipeline Context
* Append stage events
* Record execution metrics

Stages are orchestration components, not business services.

---

# 9. Internal Stage Structure

Each stage package follows the same structure.


The stage package contains orchestration artifacts only.

Business handlers reside in the Application Layer.

# 14. Handler Responsibilities

Application Handlers are responsible for:

* Coordinating domain services
* Invoking repositories
* Applying business policies
* Publishing application events
* Returning typed results

Handlers encapsulate the application use case.

---

# 15. Policies

Handlers may depend on policies such as:

* DuplicateDocumentPolicy
* SupportedFileFormatPolicy
* UploadSizePolicy
* VersioningPolicy

Policies externalize configurable business rules.

---

# 16. Events

Two categories of events are produced.

## Pipeline Events

* StageStarted
* StageCompleted
* StageFailed
* PipelineCompleted

These describe workflow execution.

## Application Events

* DocumentValidated
* DocumentStored
* MetadataExtracted
* DocumentRegistered
* DocumentIndexed

These describe completed business operations.

Application events are produced by handlers and may be consumed by downstream workflows.

---

# 17. Error Handling

Pipeline stages translate technical failures into pipeline exceptions while application handlers translate business failures into application exceptions.

This separation ensures that workflow orchestration and business logic remain independently testable.

---

# 18. Testing Strategy

Testing occurs at multiple levels.

### Stage Tests

Verify that stages:

* Create the correct Commands or Queries
* Dispatch messages through the appropriate Bus
* Update the Pipeline Context correctly

### Handler Tests

Verify:

* Business rules
* Repository interactions
* Policy enforcement
* Event generation

### Pipeline Tests

Verify:

* Correct execution order
* Context propagation
* Checkpoint handling
* Recovery behavior

### End-to-End Tests

Validate complete document ingestion from upload to indexed ManagedDocument.

# 20. Guiding Principle

The Document Management Pipeline is a workflow orchestrator, not a business service.

Its sole responsibility is to coordinate the execution of document ingestion by dispatching Commands and Queries to the Application Layer, updating the Pipeline Context with typed results, and recording workflow progress.

Business rules, repository interactions, and infrastructure concerns remain isolated within the Application Layer and Domain Layer, ensuring a modular, reusable, and enterprise-grade implementation that can be invoked consistently by pipelines, APIs, command-line tools, background workers, or AI agents.
