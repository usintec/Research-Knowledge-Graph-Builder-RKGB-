# Research Knowledge Graph Builder (RKGB)

# Processing Engine Specification

## Document 05.3 — Pipeline Definition Language (Pipeline DSL)

**Version:** 1.0

---

# 1. Purpose

The Pipeline Definition Language (Pipeline DSL) is the declarative specification used to describe processing pipelines within the RKGB platform.

Rather than embedding execution logic in source code, pipelines are defined as structured configuration documents interpreted by the Execution Planner.

This approach enables configurable, reusable, and extensible processing workflows while preserving a stable execution engine.

---

# 2. Design Goals

The Pipeline DSL is designed to:

* Separate workflow definition from implementation
* Eliminate hard-coded stage sequences
* Enable pipeline reuse across domains
* Support conditional execution
* Enable feature flags
* Support parallel execution
* Enable checkpoint configuration
* Support AI-generated pipelines
* Prepare for visual workflow editors

---

# 3. Position in the Architecture

```text
Workflow
      │
      ▼
Pipeline Definition (DSL)
      │
      ▼
Execution Planner
      │
      ▼
Execution Plan
      │
      ▼
Execution Runtime
      │
      ▼
Pipeline Stages
```

The Workflow selects a Pipeline Definition. The Execution Planner interprets it.

---

# 4. Core Concepts

The DSL introduces the following concepts:

| Concept        | Description                    |
| -------------- | ------------------------------ |
| Pipeline       | Complete processing definition |
| Node           | A processing stage             |
| Edge           | Dependency between nodes       |
| Condition      | Rule controlling execution     |
| Retry Policy   | Retry configuration            |
| Checkpoint     | Persistence boundary           |
| Parallel Group | Concurrent execution set       |
| Variables      | Runtime parameters             |

---

# 5. Pipeline Structure

A Pipeline Definition contains:

* Metadata
* Global configuration
* Stage nodes
* Dependencies
* Execution policies
* Runtime variables

The definition is declarative and contains no executable code.

---

# 6. Pipeline Metadata

Typical metadata includes:

* Pipeline identifier
* Name
* Version
* Description
* Author
* Tags
* Domain
* Created date
* Last updated
* Compatibility version

Metadata supports discovery, governance, and versioning.

---

# 7. Stage Nodes

Each node represents one Pipeline Stage.

A node specifies:

* Unique identifier
* Stage implementation
* Enabled status
* Execution timeout
* Retry policy
* Checkpoint behavior
* Resource requirements
* Parallel execution capability

The node references an implementation but does not contain business logic.

---

# 8. Dependencies

Dependencies define execution order.

Example

```text
Validate
      │
      ▼
Parse
      │
      ├─────────┐
      ▼         ▼
NER      Citation Extraction
      │         │
      └────┬────┘
           ▼
    Graph Builder
```

The Execution Planner constructs a Directed Acyclic Graph (DAG) from these dependencies.

---

# 9. Conditional Execution

Nodes may execute only when specified conditions evaluate to true.

Examples include:

* Language equals English
* PDF contains references
* OCR required
* Graph export enabled
* Embedding generation requested

Conditions allow a single pipeline definition to support multiple execution paths.

---

# 10. Feature Flags

Feature flags enable or disable capabilities without modifying the pipeline structure.

Examples

* Enable RDF export
* Enable OWL generation
* Enable GraphRAG indexing
* Enable citation validation

Feature flags support experimentation and incremental rollout.

---

# 11. Parallel Execution

Independent nodes may be grouped for concurrent execution.

Typical examples include:

* Named Entity Recognition
* Keyword Extraction
* Section Detection
* Citation Extraction

The Execution Planner schedules compatible nodes in parallel while respecting dependencies.

---

# 12. Checkpoint Policies

Each node defines whether execution state should be persisted after completion.

Checkpoint policies support:

* Restart after failure
* Long-running workflows
* Distributed execution
* Auditability

Checkpoint behavior is interpreted by the Execution Runtime.

---

# 13. Retry Policies

Retry configuration is declared per node.

Typical parameters include:

* Maximum attempts
* Retry interval
* Exponential backoff
* Retryable exception types

Retry logic remains the responsibility of the Execution Runtime.

---

# 14. Runtime Variables

Pipelines may define variables evaluated at execution time.

Examples

* Language
* Processing profile
* Confidence threshold
* Target ontology
* Export format

Variables allow one pipeline definition to serve multiple use cases.

---

# 15. Execution Profiles

Different execution profiles may reference the same Pipeline Definition.

Examples

* Fast processing
* Standard processing
* Comprehensive processing
* GPU-accelerated processing

Profiles adjust runtime behavior without changing the workflow definition.

---

# 16. Versioning

Pipeline Definitions are versioned independently.

Versioning enables:

* Reproducible processing
* Historical replay
* Safe upgrades
* Controlled migration

Older workflows may continue using previous pipeline versions.

---

# 17. Validation

Before execution, the Execution Planner validates the Pipeline Definition.

Validation includes:

* Missing stage references
* Circular dependencies
* Invalid conditions
* Duplicate node identifiers
* Unsupported configuration
* Version compatibility

Only valid pipeline definitions produce an Execution Plan.

---

# 18. AI-Generated Pipelines

Because the DSL is declarative, AI agents can generate or modify pipeline definitions.

Example scenarios include:

* Creating a domain-specific processing pipeline
* Adding or removing stages
* Optimizing execution order
* Selecting optional capabilities
* Generating research-specific workflows

The generated definition is validated before execution.

---

# 19. Visual Pipeline Editors

The DSL serves as the persistence format for future visual editors.

Users may construct workflows graphically, while the editor generates a valid Pipeline Definition.

Conversely, existing definitions may be visualized as execution graphs.

---

# 20. Knowledge Graph Integration

Pipeline Definitions are themselves domain artifacts.

Pipelines, stages, dependencies, and execution metadata may be represented within the semantic knowledge graph.

This enables:

* Pipeline discovery
* Dependency analysis
* Workflow analytics
* Impact assessment
* Governance

---

Phase 3

* Multi-agent collaboration

Phase 4

Phase 5

The DSL remains the stable description of business workflows regardless of the execution engine.

---

# 22. Guiding Principle

The Pipeline Definition Language is the declarative contract between business intent and execution.

It allows workflows to be described rather than programmed, enabling reusable, configurable, AI-generated, and future visual processing pipelines while preserving a stable and extensible execution engine.

By treating pipeline definitions as first-class architectural artifacts, RKGB establishes a foundation for scalable AI processing, semantic knowledge graph construction, GraphRAG, autonomous research agents, and distributed workflow orchestration.
