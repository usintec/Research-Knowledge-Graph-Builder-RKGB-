# RKGB (Research Knowledge Graph Builder)

# AI Engineering Implementation Prompt

## Step A3 — Logging & Observability Framework (Phase 1)

You are continuing the implementation of the Research Knowledge Graph Builder (RKGB).

The project bootstrap (Step A1) and Configuration System (Step A2) have already been completed.

Do **NOT** redesign the architecture.

Implement only the Logging & Observability Framework (Phase 1).

This is **not** just a logging module.

It is the foundation of the platform's observability strategy.

The framework must be enterprise-grade, structured, extensible, dependency-injection friendly, and capable of supporting future distributed deployments.

---

# Architectural Context

RKGB follows:

```text id="kg4f9d"
Presentation Layer
        │
        ▼
Processing Engine
        │
        ▼
Application Layer
        │
        ▼
Domain Layer
        │
        ▼
Repository Layer
        │
        ▼
Infrastructure Layer
```

The Logging Framework belongs to the Infrastructure Layer.

Every other layer depends on it.

No layer should instantiate Python loggers directly.

# Logging Manager

Implement a Logging Manager responsible for:

* Creating loggers
* Applying configuration
* Registering handlers
* Managing formatter selection
* Managing log levels
* Providing logger instances through Dependency Injection

Only one manager should exist per application instance.

---

# Logger Factory

Implement a Logger Factory responsible for:

* Creating component-specific loggers
* Applying contextual information
* Injecting correlation identifiers
* Returning strongly configured logger instances

Consumers should never create loggers manually.

---

# Structured Logging

All logs must be structured.

Every log entry should support fields such as:

* Timestamp
* Level
* Logger name
* Message
* Correlation ID
* Trace ID
* Pipeline ID
* Stage ID
* Execution ID
* Command name
* Query name
* Event name
* User (future)
* Plugin (future)
* Exception details (when applicable)

Design the framework so additional fields can be added without changing business code.

---

# Correlation Context

Implement a context object capable of flowing through the system.

Example:

```text id="8sh4tg"
Request

↓

Pipeline

↓

Stage

↓

Command

↓

Handler

↓

Repository
```

Every component should inherit the same Correlation ID.

This enables end-to-end traceability.

---

# Pipeline Context Integration

The Logging Framework must integrate with the existing Pipeline Context.

Every stage execution should automatically log:

* Stage started
* Stage completed
* Stage duration
* Stage failure
* Retry attempt
* Checkpoint creation

The pipeline itself should not perform logging logic manually.

---

# Command Bus Integration

Prepare the framework so the future Command Bus can automatically log:

* Command dispatched
* Handler resolved
* Handler execution started
* Handler completed
* Handler failed
* Execution duration

No implementation of the Command Bus is required.

Only prepare the logging abstractions.

---

# Query Bus Integration

Prepare support for:

* Query dispatched
* Query handler resolved
* Query completed
* Execution duration

---

# Event Bus Integration

Prepare support for:

* Event published
* Subscriber invoked
* Subscriber completed

* Correlation ID
* Pipeline ID (if available)
